# deterministic-nutrient-tools Specification

## Purpose

Deterministic, lookup-table-driven functions for the nutrient arithmetic the assistant
needs — BMI, calorie targets, protein targets, food lookup, and meal nutrition totals —
so that no nutrient number a user sees was generated by the language model.

## Requirements

### Requirement: Nutrient calculations never invoke the language model

The system SHALL compute BMI, calorie targets, protein targets, and meal nutrition
totals using deterministic Python functions only. No nutrient-calculation tool SHALL
call the language model, and the same input SHALL always produce the same output.

#### Scenario: Repeated calls are identical

- **WHEN** `calculate_calorie_target` is called twice with the same age, weight, sex,
  and activity level
- **THEN** both calls return the same numeric result

#### Scenario: No model call is made

- **WHEN** any of the deterministic nutrient tools is invoked
- **THEN** no request is sent to the language model

### Requirement: Every tool validates its input before computing

Every tool SHALL accept a Pydantic-validated input and SHALL reject an invalid input
(age outside 0–60 months, non-positive weight, non-positive height, or an unrecognized
enum value) before performing any calculation (hard rule 7).

#### Scenario: Out-of-range age rejected

- **WHEN** `calculate_calorie_target` is called with an age of 72 months
- **THEN** the call is rejected as invalid
- **AND** no calorie value is returned

#### Scenario: Non-positive weight rejected

- **WHEN** any nutrient tool is called with a weight of `0` or a negative value
- **THEN** the call is rejected as invalid

### Requirement: `calculate_bmi` computes BMI from weight and height

The system SHALL compute BMI as weight in kilograms divided by height in metres
squared, given as call parameters rather than read from a stored profile. The result
SHALL state that a child's BMI is interpretable only as an age- and sex-specific
percentile and SHALL direct the reader to `assess_growth` for it.

#### Scenario: BMI computed from valid inputs

- **WHEN** `calculate_bmi` is called with a positive weight in kilograms and a positive
  height in centimetres
- **THEN** the returned BMI equals weight_kg / (height_m ^ 2), rounded to two decimal
  places

#### Scenario: Result points to the percentile tool

- **WHEN** `calculate_bmi` returns
- **THEN** its note names `assess_growth` as the way to obtain the percentile

### Requirement: `calculate_calorie_target` and `calculate_protein_target` use age-banded reference values

The system SHALL compute calorie and protein targets using the age-banded formulas and
reference values published in recognized dietary reference intake guidance, matching the
same figures already cited in the knowledge base (hard rule 5 provenance carries into
tool output).

#### Scenario: Targets fall within the published reference range for the age band

- **WHEN** `calculate_protein_target` is called for a child aged 8 months
- **THEN** the returned target is derived from the 7–12 month reference value
- **AND** the response names the reference source

#### Scenario: Targets differ across age bands

- **WHEN** `calculate_calorie_target` is called for a 6-month-old and again for a
  4-year-old with realistic weights for each age
- **THEN** the two returned targets differ, reflecting the different reference values
  for each age band

### Requirement: `lookup_food` and `calculate_meal_nutrition` read only from the food-composition table

`lookup_food` SHALL return a food's nutrient and safety record by identifier or by the
food's common name as the parent said it, resolved deterministically by the
food-composition table's resolution rules — never by language-model guessing. It SHALL
accept an optional quantity and unit (`g` or `ml`); when a quantity is given the result SHALL
also carry the nutrients for exactly that amount, computed in code as the quantity divided
by the table serving size times the per-serving values, alongside the per-serving record. A
unit that contradicts the food's table unit SHALL be refused naming the food's unit; a
quantity without a unit SHALL be read in the food's own unit and the unit used SHALL be
echoed in the result. `calculate_meal_nutrition` SHALL sum the nutrient values of a list of
foods and quantities, using only values present in the food-composition table, accepting
each food by identifier or common name under the same resolution rules, and accepting each
item's amount either as servings (multiples of the table serving) or as a quantity with unit
under the same rules. A string the table refuses to resolve SHALL surface as the tool's
not-found outcome with the string preserved as given.

#### Scenario: Meal nutrition sums correctly

- **WHEN** `calculate_meal_nutrition` is called with two foods and their quantities
- **THEN** the returned totals equal the sum of each food's nutrients scaled by quantity

#### Scenario: Unknown food in a meal is reported, not silently skipped

- **WHEN** `calculate_meal_nutrition` is called with a food identifier not in the table
- **THEN** the call reports which identifier was not found
- **AND** does not silently omit it from the total without reporting it

#### Scenario: Lookup by common name

- **WHEN** `lookup_food` is called with "bananas" and the table's only banana entry is
  `banana_mashed`
- **THEN** the tool returns the `banana_mashed` record with its nutrients, safety flags,
  and source

#### Scenario: Meal item by common name

- **WHEN** `calculate_meal_nutrition` is called with an item naming "bananas"
- **THEN** the item is resolved and counted in the totals

#### Scenario: Ambiguous name fails the lookup rather than guessing

- **WHEN** `lookup_food` is called with a name matching more than one table entry
- **THEN** the call fails as not-found, naming the candidate entries
- **AND** no entry is silently chosen

#### Scenario: Lookup with a quantity scales deterministically

- **WHEN** `lookup_food` is called with "sweet potato", quantity 20 and unit `g`, and the
  entry's serving is 60 g
- **THEN** the result carries the per-serving record and, separately, the nutrients for
  20 g equal to the per-serving values times 20/60
- **AND** the result echoes the requested quantity and unit

#### Scenario: Quantity in the wrong unit is refused

- **WHEN** `lookup_food` is called with a food measured in grams and a quantity in `ml`
- **THEN** the call fails naming the food and that it is measured in grams
- **AND** no nutrient figures are returned

#### Scenario: Meal item by quantity

- **WHEN** `calculate_meal_nutrition` is called with an item giving 150 ml of a food whose
  serving is 100 ml
- **THEN** the item counts as 1.5 servings in the totals

### Requirement: Feeding-log tools join the deterministic tool set

The system SHALL expose `log_feeding`, `get_daily_nutrition`, `get_remaining_targets`,
and `detect_nutrient_gaps` as deterministic tools with typed, validated inputs, subject to
the same requirements as the existing tools: no language-model arithmetic, validation
before computation, and results that carry their source. `log_feeding` SHALL validate and
normalise an entry and return it with its identifier and table-derived nutrients, and
SHALL NOT persist anything until the feeding-log table ships.

#### Scenario: Eleven tools with typed schemas

- **WHEN** the tool set is built
- **THEN** it contains exactly the six existing tools plus the four feeding-log tools and
  the growth assessment, each with a typed argument schema

#### Scenario: Invalid entry rejected before computation

- **WHEN** `log_feeding` is invoked with a quantity of zero
- **THEN** the invocation is rejected by validation and no nutrient computation runs

#### Scenario: No model call for totals

- **WHEN** `get_daily_nutrition` is invoked
- **THEN** no language-model call is made

### Requirement: Every reference intake figure comes from one declarative registry

The system SHALL hold every dietary reference intake figure it uses — the per-age-band
value, its reference type (adequate intake, recommended dietary allowance, or estimated
energy requirement), its unit, its tolerable upper intake level where one is published,
and its source citation — in a single declarative registry. No reference figure SHALL be
defined in more than one place, and adding a nutrient to the registry SHALL be sufficient
to give it a target. Registry figures SHALL match the values cited in the knowledge base
for the same nutrient and age band (hard rule 5 provenance).

#### Scenario: A figure is defined exactly once

- **WHEN** the reference value for a nutrient and age band is requested twice through
  different callers
- **THEN** both callers receive the same value, reference type, band label, and source

#### Scenario: Registry figures agree with the knowledge base

- **WHEN** any registry value is compared with the corresponding published value in the
  nutrition knowledge base for the same nutrient and age band
- **THEN** the two agree

#### Scenario: Every target names its provenance

- **WHEN** a target is produced for any nutrient in the registry
- **THEN** it carries its unit, reference type, age-band label, and source
- **AND** it carries its tolerable upper intake level when one is published for that band

### Requirement: Daily targets are an ordered set selected by age and diet preference

The system SHALL produce a child's daily targets as an ordered set whose membership and
order are determined by the child's age in months and diet preference. Selection and
ordering SHALL be deterministic and SHALL involve no language-model call. Diet preference
SHALL affect only which nutrients are present and their order; it SHALL NOT change any
nutrient's reference value, because reference intakes are not diet-specific.

#### Scenario: Order responds to age

- **WHEN** targets are produced for a 9-month-old and for a 30-month-old on the same diet
- **THEN** both sets are ordered by the child's age-appropriate priority
- **AND** iron precedes protein for the 9-month-old, reflecting the sharp rise in iron
  need from 7 months

#### Scenario: Membership responds to diet preference

- **WHEN** targets are produced for a vegan child and for an omnivorous child of the same
  age and weight
- **THEN** the vegan child's set additionally contains vitamin B12
- **AND** every nutrient present in both sets carries an identical reference value

#### Scenario: Selection is deterministic

- **WHEN** targets are produced twice for the same age, weight, sex, and diet preference
- **THEN** the two sets are identical in membership, order, and values

#### Scenario: An advisory nutrient carries guidance instead of a number

- **WHEN** targets are produced for a vegan child
- **THEN** the set contains an omega-3 DHA entry that carries guidance text, a source, and
  a publication date, and carries no numeric target
- **AND** that entry is never compared against logged intake

### Requirement: Each target declares whether logged intake is compared against it

Each target SHALL declare whether the feeding log can observe intake for that nutrient.
A nutrient SHALL be declared trackable only when the food-composition table supplies a
per-food value for it and the child's diet permits a food in the table that provides it.
A target that is not trackable SHALL carry a parent-facing reason and SHALL NOT be given
an average, a ratio, or a flag anywhere in the system.

#### Scenario: Vitamin D is displayed but never scored

- **WHEN** targets are produced for a child of any age
- **THEN** vitamin D carries a numeric target, its reference type, and its source
- **AND** it is marked not trackable, with a reason stating that intake comes from
  supplements and sunlight rather than logged food
- **AND** it carries no average, ratio, or flag

#### Scenario: Vitamin B12 carries diet-appropriate guidance and no score yet

- **WHEN** targets are produced for a vegetarian child and for a vegan child
- **THEN** both entries show vitamin B12 as not trackable, because the food-composition
  table does not yet supply a per-food B12 value
- **AND** the vegan child's entry carries guidance that every vegan child needs a B12
  supplement or reliably fortified foods
- **AND** the vegetarian child's entry notes that dairy and eggs usually cover B12

#### Scenario: A non-trackable target cannot carry a flag

- **WHEN** any target marked not trackable is produced
- **THEN** the system rejects it as invalid if an average, ratio, or flag is attached

### Requirement: `assess_growth` joins the deterministic tool set

The system SHALL expose `assess_growth` as a deterministic tool with a typed, validated
input (age in months, sex, weight, optional length/height), subject to the same
requirements as the existing tools: no language-model arithmetic, validation before
computation, and results that carry their source. Its behaviour is specified by the
`growth-assessment` capability.

#### Scenario: Tool present with a typed schema

- **WHEN** the tool set is built
- **THEN** it contains `assess_growth` alongside the existing tools, with a typed argument
  schema that marks length/height optional

#### Scenario: Invalid input rejected before computation

- **WHEN** `assess_growth` is invoked with a sex value outside the vocabulary
- **THEN** the invocation is rejected by validation and no lookup runs

#### Scenario: No model call

- **WHEN** `assess_growth` is invoked
- **THEN** no language-model call is made
